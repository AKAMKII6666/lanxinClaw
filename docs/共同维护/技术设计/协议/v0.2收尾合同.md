# 协议 0.2：状态一致与关闭确认

本页记录产品 V1.0 收尾的当前合同；phone 与 companion 必须配套升级。0.1 业务帧由 envelope 校验拒绝，不执行部分业务。部署前备份两端运行数据，回滚需恢复匹配代码和必要数据快照。

## 状态真源

`packages/protocol/src/states/` 是唯一迁移表维护源；`npm run sync:phone-contract` 生成 phone 仓库携带的 JSON，`npm run check:phone-contract` 检查漂移。实机运行不依赖邻接源码仓库。

即时完成不是放宽 `needs_permission→completed`。已授权 runtime 确实接收后先投递 `job.accepted/running`，再投递已获得的终态。提交失败不广播成功、不结束结果跟踪。`queued→failed` 仅用于明确的提交拒绝/发送失败；等待 ack 超时不等于执行失败。

## 请求回执

JSON 回执不是业务 envelope。owner 为 companion 请求处理器，方向为 companion→已发起请求的 phone socket，认证沿用该 socket 的 session 与设备绑定。

所有可识别请求均以 `correlationId` 绑定原 `messageId`。成功携带 `acceptedType`，失败携带 `rejectedType` 和稳定 `error.code/message/retryable`。无法解析的帧允许关联字段为 null。phone 必须在发送之前登记精确等待器，不得按消息类型或任意失败回执匹配并发请求。

schema：`result-ack.schema.json`；TypeScript：`ProtocolResultAck`；校验：`validateProtocolResultAck`。

## 关闭请求与已提交事实

同一 `affair.close` 类型按方向有两种不同载荷：

| 字段/载荷 | owner | 方向与认证 | 语义 |
|---|---|---|---|
| `affairId` | 请求方 | phone→companion，已认证 session | 明确目标事务 |
| `status` | 请求方 | 同上 | `closed` 为验收，`canceled` 为取消 |
| `expectedCurrentJobId` | 请求方观察值 | 同上 | 明确 job ID 或 null；companion 对照当前事实拒绝过期请求 |
| `acceptanceSummary` | 用户经张老板/桌面确认 | 同上/本地受限 bridge | 验收必填，记录用户接受的依据 |
| `closeReason` | 请求方 | 同上 | 可选取消原因 |
| `{affair,jobs}` | companion | companion→phone，已认证目标 | 已提交父事务与该事务全部子 job 事实；并作为成功 ack 的 `result` |

请求不能携带旧 title/context/完整事务快照覆盖当前事实。成功结果中的子 job 都必须停止；验收要求当前 execution job 为 completed、evidenceQuality=present 且 resultDigest 非空，探索任务不能验收。schema 负责形状，业务 validator/协调器负责 ID 归属及当前状态关系。

共同协调器拥有关闭权威。UI 与 WS 走相同入口；通用 `affair.update`、通用出站函数及 store apply 不能发起关闭。取消顺序为：持久化 pending 围栏→等待同事务在途委派→撤销权限→确认所有子 job 停止→原子保存父终态及请求结果→广播/ack。既有 completed/failed job 保留真实状态。

执行器不可用、取消仅 accepted、写盘失败都不能提交假终态。pending 围栏阻止新增 job/授权，已取消的外部效果不回滚，原请求恢复后继续剩余步骤。同事务操作串行，heartbeat 不等待业务队列。

幂等键为设备 ID 与请求 messageId。原键不得换内容。结果与父终态同镜像保存，ack 丢失后重连/重启返回原结果，不重复执行。phone 持久化原请求及回执；先保存证明，再以完整结果补齐断线期间遗漏的中间事件。未确认只能回报待确认，不能声称双方已经关闭。

相关 schema 为 `affair-close.schema.json` 与 `affair-action-result.schema.json`。0.2 不兼容 0.1 的完整事务关闭命令或无关联 ack。

## 消息归属与消费证明

- `chat.message`/`chat.context_attach` 的源 ID、原文、显式 affairId 不可在重试中替换。无 affairId 保持未归属。桌面自由输入只发送文字；phone 与用户讨论后用本地 `companion.bind_message(message_id, affair_id, user_confirmation_summary)` 记录一次明确归属，不授予执行权限。
- Companion 拥有出站队列和消费确认；发送前持久化原消息 ID 与配对收件设备。重连复用原 ID，直到认证来源匹配的消费回执与出队共同提交。无来源身份的旧队列保留供核对，不自动重定向。
- Phone 拥有独立原文收件箱，以来源设备、消息类型、源 ID 去重；旧版 pending 按原事务导入。`received → injecting → delivered` 表示向 realtime 交付，不能据此声称用户已听到。发送结果不明或进程在 injecting 中退出转为 ambiguous，先核对，不自动重播。
- `companion.fetch_pending_context` 只查询；没有参数返回未消费项，affair_id 只筛选明确绑定项，message_id 可找回任意已保存完整原文。工具输出确实进入实时连接后才能记录 delivered。ambiguous 项默认不返回正文以避免重复转述，明确 ID 查询仍保留待核对标志。
- `chat.read_receipt` 方向 phone→companion，要求认证 session；必须且只能携一个 chatMessageId/attachId 和真实交付时间 readAt。原回执请求 ID 持久化，收到对应 result-ack 才记确认。失败或丢 ack 只重试回执，不重复交付内容。
- 本批新增 FC 为 phone 本地数据归属操作；wire receipt 字段不增加，互斥约束与 paired 0.2 一起启用；旧业务帧拒绝后提示两端同步升级。

## 新任务与当前执行对象

明确 job.create 由 companion 在事务队列内校验；当前 execution job 未停止时拒绝替换。旧执行已停止后，新 job、currentJobId 与请求去重记录共同保存；落盘失败回滚。探索不会抢占已有 execution job，旧 job 事件不能改变当前执行对象。该规则不增加 wire 字段，由既有 job.create owner companion 负责；认证与版本要求沿用 0.2。

# 质量门禁

质量门禁把项目规则变成可执行检查。它们不替代 review，但必须挡住明确的结构退化。

## 统一入口

根命令是：

```bash
npm run quality
```

它会运行：

- `check:docs-layout`
- `check:language`
- `check:structure`
- `check:comments`
- 门禁自测（`test:quality`）
- `test:protocol`（`packages/protocol` contract / examples 测试）
- `test:mock-companion`（mock companion 事件流与 UI 契约测试）

后续 typecheck、真实 companion / adapter integration tests 也必须接入同一个统一入口。

## 结构门禁

第一版结构门禁检查：

- 禁止 co-located tests。
- 禁止 internal barrels。
- 目录聚类。
- 文件有效行数限制。
- 函数有效行数限制。
- 近似 cyclomatic complexity。
- broad allowlist entries。
- 排除已知 generated/build directories。

## 阈值

| Kind | Warn | Hard |
|------|-----:|-----:|
| protocol file | 250 | 400 |
| companion file | 300 | 450 |
| UI file | 220 | 350 |
| route/page file | 120 | 200 |
| other source file | 350 | 500 |
| test file | 450 | 700 |
| function | 50 | 90 |
| complexity | 10 | 15 |

有效行数忽略空行，但包含注释。注释是可维护性的一部分，不得为了通过门禁删除注释。

## 注释门禁

第一版注释门禁检查 strict contract directories：

- `packages/protocol/src`
- `packages/openclaw-adapter/src`
- `apps/companion/src/bridge`
- `apps/companion/src/pairing`
- `apps/companion/src/permissions`
- `apps/companion/src/credentials`

Strict file 必须有文件头注释，说明：

- 模块职责。
- 不拥有的职责。
- 是否 pure，或会产生哪些 side effect。

Strict file 中的 exported function 必须有就近 JSDoc，包含：

- 每个 declared parameter 的 `@param`。
- 当 return type 不是 `void`、`undefined` 或 `never` 时，需要 `@returns`。

Strict file 中 exported `interface` 与 object-shaped `type` declaration 必须有字段级注释。

门禁也拒绝明显无效注释和无原因 suppress：

- `eslint-disable`
- `@ts-ignore`
- `@ts-expect-error`

## 语言门禁

项目文档和注释默认使用中文。专业名词、协议字段、API、命令、路径、message type、permission id 可以保留英文。

第一版语言门禁检查：

- Markdown / mdc 正文不能整段英文。
- 代码注释不能整段英文。
- code fence、JSON、schema、路径、命令和字段名不按自然语言检查。

## Allowlist 规则

Allowlist entry 必须集中登记在 quality gate config 中，并包含：

- `ruleId`
- `target`
- `reason`
- `owner`
- `createdAt`
- `exitCondition`

不允许 `apps/**`、`packages/**`、`src/**`、`**/*` 等 broad target。

## 脚本自测

质量门禁脚本必须有自己的测试。无法证明自己能抓住失败的门禁，不应作为 hard rule。

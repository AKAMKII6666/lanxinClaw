# 携证状态转移原则

## 0. 文档定位

本文用于指导澜星 Claw 的状态机、协议消息、异步事件、权限裁决和执行引擎状态映射设计。

本文是软监督原则，不替代已固化的协议、schema、状态机或安全模型：

- 具体字段、枚举、消息方向、认证要求仍以 [协议/说明.md](协议/说明.md)、[安全模型.md](安全模型.md) 和 JSON Schema 为准。
- 本文不因形式不一致单独阻断开发；若发现会造成权限绕过、错误终态、重放推进或凭据泄露，应按安全、协议和质量规则阻断。
- 采用额外字段、代际或日志前，必须说明它关闭的具体风险；不得为了“看起来更安全”增加无人校验、无人消费的字段。

## 1. 核心抽象

**携证状态转移** 指：每一次跨边界或高风险状态推进，都必须携带足以判断“身份正确、对象正确、上下文仍有效、前置条件已满足、操作仍允许”的证据；接收方必须验证这些条件后，才能提交状态变化。

这里的“证”不是特指密码学证明，可以是：

- pairing / session 认证结果；
- `affairId`、`jobId`、`permissionRequestId`、`messageId`、`correlationId` 等关联标识；
- 当前状态机里可原子检查的前置状态；
- companion permission gate 的授权记录；
- adapter / runtime 返回的受信状态断言；
- 可判断请求未过期、未取消、未被替代的围栏条件；
- 脱敏 audit / timeline 记录。

目标是防止：

- worker 中间信号被误判成 affair 完成；
- 迟到、重复或重放消息推进旧状态；
- 未配对或已撤销设备继续开 session；
- renderer 或 phone 绕过 companion 权限层；
- 取消、暂停、恢复和重试造成重复副作用；
- mock 或默认值制造“真实链路成功”的假象；
- 事故后无法还原为何允许该状态转移。

## 2. 适用范围

出现下列任一情形时，应主动应用本文：

- pairing、session、affair、job、permission 的状态机设计或实现；
- phone ↔ companion、companion ↔ adapter、adapter ↔ OpenClaw runtime 的消息或事件；
- `job.completed`、`affair.close`、cancel、resume、retry 等终态或准终态；
- permission gate、设备身份、凭据状态、workspace scope 等安全边界；
- WebSocket / HTTP 断线重连、轮询、stream、异步回调或事件重放；
- mock runtime、local-safe runtime 与真实 Gateway / SDK 的切换；
- 协议正文、schema、examples、mapper、tests 之间的同步。

纯展示样式、静态文案、无状态局部组件，默认不扩大套用本文。

## 3. 澜星十二条原则

### 原则 1：成功态必须有完整门闩

任何用户可见或不可逆成功态，只能在全部必要前置条件确认后写入。

- `job.completed` 只能证明 worker 完成，不能证明 affair 已关闭。
- `affair.closed` 只能由用户验收后产生；用户明确取消时走 `canceled`。
- pairing 发现、端口可连、设备名匹配，不能证明已配对或已授权。

### 原则 2：跨边界消息必须可关联、可判旧

可能延迟、重试或重放的消息，必须能关联到当前有效的 affair、job、session、permission request 或 message。

- 接收方不得只靠“消息刚到”判断它仍有效。
- 已取消、已终态、已撤销 pairing、已被新 job 替代的旧消息不得推进当前状态。
- 消息处理应使用 `messageId` / `correlationId` / `affairId` / `jobId` 做幂等与追踪。

### 原则 3：高风险副作用必须先验证后提交

文件、命令、git、网络、桌面控制和 OpenClaw 委派，必须先通过 companion 权限层，再提交状态变化。

- 不得先写 `running` 或 `completed`，再补权限校验。
- 权限请求、授权记录和执行范围应在同一受控流程里绑定。
- 任一步失败时，不得留下对 phone 或 UI 可见的假成功态。

### 原则 4：终态必须单调

`closed`、`canceled`、job 终态和 revoked identity 不得被迟到事件复活。

- `closed` / `canceled` 无出边。
- revoked pairing identity 不得因发现到同一设备名而恢复。
- 已取消 job 的迟到 progress / completed 不得覆盖取消结果。

### 原则 5：业务事实必须有唯一真源

事务事实、执行事实、权限事实、连接事实和 UI 投影是不同事实。

- 电话侧 affair store 拥有 affair 连续性和最终关闭。
- companion 拥有 pairing、session、permission 和桌面副作用门禁。
- adapter / OpenClaw runtime 只拥有 worker 执行状态。
- renderer 只消费投影，不拥有授权或执行能力。

### 原则 6：控制面 fail-closed

身份、权限、凭据、运行模式、执行范围或状态前置无法确认时，默认拒绝操作。

- 不得用 development、mock 或 local-safe 静默替代真实 Gateway 并报告真实成功。
- 不得用按钮隐藏、UI 文案或本地缓存代替 companion host 校验。
- workspace scope 无法判断时，禁止执行文件、命令、git 或网络副作用。

### 原则 7：展示面不得伪装控制面

控制面板可以展示降级、空态或 demo 数据，但不得让用户误以为真实权限、真实 Gateway 或真实 phone 链路已完成。

- UI 可 fail-open 展示安全占位。
- 授权、执行、配对和关闭必须 fail-closed。
- demo / mock 标识不得被业务逻辑当作真实链路证据。

### 原则 8：Mock 不得作为运行时降级

Mock 只用于明确的开发、测试或演示入口，不能掩盖真实服务故障。

- mock companion 验收不能替代真实 desktop companion protocol server 验收。
- mock runtime / local-safe runtime 不能替代真实 OpenClaw Gateway 联调验收。
- mock 与真实实现必须保持外部合同同构。

### 原则 9：操作能力由可信 owner 显式决定

Cancel、resume、retry、close、permission decision 等能力，应由对应 owner 的当前状态决定，并在执行时重新校验。

- renderer 不得推断“按钮可点”就代表权限已授予。
- phone 不得推断“张老板同意”就代表电脑端副作用已授权。
- adapter 不得推断 runtime 可执行就代表 companion 已授权。

### 原则 10：高风险链路必须包含反例测试

测试不仅证明正常路径能完成，也要证明错误输入和异常时序不能推进错误状态。

至少按风险覆盖：

- 重复消息、重复提交、重复回调；
- 迟到 progress / completed；
- 已取消、已暂停、已终态对象；
- 未配对、authProof 错误、identity revoked；
- 权限缺失、scope 越界、unknown permission；
- mock / real 切换错误；
- 协议未知字段、缺必填、非法状态迁移。

### 原则 11：协议载体必须一致

协议正文、字段表、schema、examples、wire DTO、mapper、mock、测试必须表达同一合同。

- 示例是合同的一部分，不得成为第二套协议。
- 新增协议字段必须说明 owner、方向、认证要求和兼容策略。
- 修改状态语义时必须同步状态机、schema、文档和反例测试。

### 原则 12：关键动作必须可追踪且脱敏

异步和高风险链路应保留足够上下文，用于还原“为何允许或拒绝这次操作”。

可追踪信息包括：

- pairing / session / affair / job / permission request 标识；
- 状态迁移前后值；
- 权限决策与 scope 摘要；
- runtime run id 与安全进度摘要；
- 机器可读错误码；
- 关键前置检查结果。

audit、timeline、日志、示例和测试快照不得记录 API key、token、pairing secret、设备私钥或完整 secret。

## 4. 高风险设计检查

涉及状态机或跨边界事件的方案，应回答：

1. 谁在操作：可信身份和认证结果来自哪里？
2. 操作什么：affair、job、permission、session 如何关联？
3. 针对哪一代：如何判断事件没有过期、取消或被替代？
4. 凭什么推进：状态机前置条件和权限证据是什么？
5. 现在还能否执行：终态、暂停、撤销、超时如何处理？
6. 重复执行会怎样：幂等键和副作用去重在哪里？
7. 失败一半会怎样：是否会留下假成功或半完成状态？
8. 之后如何解释：audit / timeline / error code 是否足够且脱敏？

若某项不适用，应说明原因；不得为了形式补造复杂机制。

## 5. 冲突处理

当本文与现有协议、实现成本或阶段范围发生张力时，不得默默选择一方。应说明：

```markdown
### 冲突
- 当前方案：
- 触发原则：
- 可能风险：
- 现有补偿控制：

### 选项
1. 方案 A：影响范围、收益、成本和残余风险
2. 方案 B：影响范围、收益、成本和残余风险

### 建议
- 推荐：
- 理由：
- 是否触及现有硬规则或协议：
- 若暂缓，如何登记和验证：
```

裁决优先级：

1. 凭据安全、设备身份、桌面权限边界；
2. 协议兼容性与状态机正确性；
3. affair/job/permission 事实真源清晰；
4. 可测试性、可诊断性与可追踪性；
5. 实现复杂度与交付效率；
6. 局部代码风格。

## 6. 禁止机械套用

禁止：

- 为低风险 UI 或局部纯函数引入不成比例的状态基础设施；
- 新增无人消费、无人校验、无人审计的“证据字段”；
- 把受信断言说成独立验证；
- 用本文覆盖已明确的协议语义；
- 把未来增强包装成当前必做项；
- 只增加日志而不建立实际校验；
- 只隐藏前端入口而不保护 companion / adapter 的高风险动作。

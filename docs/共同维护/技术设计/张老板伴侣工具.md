# 张老板 Companion FC 设计

> 适用范围：v1.3 P7。本文定义张老板在电话侧可调用的 companion 相关 Function Call（FC / tool）目录。  
> Wire 真源仍是 [协议/消息目录.md](协议/消息目录.md)；FC **不是**新的 envelope type，而是把 LLM tool 调用翻译成已有 phone↔companion 消息，并读写 [电话侧事务簿.md](电话侧事务簿.md)。  
> 共享枚举见 `packages/protocol` 的 companion FC catalog。

## 1. 目标与非目标

### 目标

张老板通过一组窄 FC 完成：

- 创建 job
- 查询进度
- 暂停 affair
- 恢复 affair
- 取消 job / affair
- 发送或消费 chat context

从而在挂机后仍能推进事务，而不直接操作电脑。

### 非目标

- FC 不得绕过 companion 执行文件、命令、git、网络或 GUI。
- FC 不得授予 permission；权限权威在 companion。
- FC 不得因 worker completed 关闭 affair。
- `chat.message` / `chat.context_attach` 文本一律 untrusted，不得当 system instructions。
- 本版不新增 `job.pause` / `job.query` 等未登记 wire type；查询走本地 store，暂停走 `affair.update`。

## 2. 分层

```text
张老板 LLM
  -> Companion FC（电话进程内 tool）
  -> Affair Store（本地） + Protocol Client（已认证 session）
  -> Companion（权限门禁）
  -> OpenClaw Adapter（worker）
```

| 层 | 职责 |
|----|------|
| FC | 参数校验、幂等键、把意图映射为 store 写 + 可选协议发送 |
| Store | 事务连续性与进度镜像 |
| Protocol | 已登记 message type；须 session 认证 |
| Companion | 配对、权限、桌面副作用 |

## 3. FC 总表

| FC name | 作用 | 写 Store | 发出的协议消息 | 认证 |
|---------|------|----------|----------------|------|
| `companion.create_job` | 为指定 affair 委派执行 | 是 | `job.create`（通常伴随 affair → `delegated` 的 `affair.update`） | session |
| `companion.get_progress` | 查询 affair/job 进度 | 否（只读） | 无（读 store；可选等待已缓冲事件） | 本地 |
| `companion.pause_affair` | 暂停事务 | 是 | `affair.update`（`status=paused`） | session |
| `companion.resume_affair` | 从 blocked/paused 恢复 | 是 | `affair.resume` | session |
| `companion.cancel_job` | 取消当前或指定 job | 是 | `job.cancel` | session |
| `companion.cancel_affair` | 用户明确取消整件事务 | 是 | `affair.close`（`status=canceled`） | session |
| `companion.send_chat_context` | 向 companion 发送精确文本侧写 | 是（timeline） | `chat.message` | session |
| `companion.fetch_pending_context` | 拉取尚未注入实时通话的桌面附加上下文 | 是（消费 pending） | 无（读 store 中 `pendingContext`；由先前 `chat.context_attach` 写入） | 本地 |

> `companion.fetch_pending_context` 是 [协议/聊天.md](协议/聊天.md) 所述 realtime 注入不可用时的 **FC fallback**。

## 4. 各 FC 契约

### 4.1 `companion.create_job`

| 项 | 内容 |
|----|------|
| 意图 | 在 context 与 acceptance criteria 足够后委派 worker |
| 入参 | `affairId`、`goal`、可选 `workspaceHint`、`allowedPermissions[]`、可选客户端 `jobId` |
| 前置 | store 中 affair 为 `ready` 或可进入 `delegated`；已有 session |
| 行为 | 生成/校验 `jobId` → store 登记 job=`queued` → 发 `job.create` → affair 倾向 `delegated` |
| 返回 | `{ jobId, affairId, status }` |
| 错误 | 无 session、非法状态迁移、缺 goal、未知 permission id 不得默认为已授权 |
| 幂等 | 同一 `jobId` 重复调用不二次委派 |

`allowedPermissions` 只是声明意图；最终是否执行由 companion permission gate 决定。

### 4.2 `companion.get_progress`

| 项 | 内容 |
|----|------|
| 意图 | 回答“到哪了 / 卡在哪” |
| 入参 | `affairId`，可选 `jobId` |
| 行为 | 只读 store：返回 affair.status、currentJobId、progressSummary、blockedReason、resumeCondition、最近 timeline |
| 不发协议 | MVP 不发明 `job.query`；进度靠已收 `job.progress` 等事件 |
| 返回 | 结构化摘要；不得编造未入 store 的成功 |

### 4.3 `companion.pause_affair`

| 项 | 内容 |
|----|------|
| 意图 | 用户或张老板主动暂停，停止自动推进 |
| 入参 | `affairId`，可选 `reason` |
| 行为 | 校验可迁到 `paused` → store 更新 → `affair.update`（status=`paused`） |
| Companion 侧期望 | 停止自动重试高风险动作；进行中 job 由 companion/adapter 安全挂起或取消策略处理（实现见后续监督任务） |
| 返回 | 更新后 status |
| 说明 | **不**新增 `job.pause` wire type |

### 4.4 `companion.resume_affair`

| 项 | 内容 |
|----|------|
| 意图 | resume condition 满足后继续 |
| 入参 | `affairId`，可选 `resumeNote` |
| 行为 | 发 `affair.resume`；store 在确认可恢复前保持 `blocked`/`paused`，收到后续 progress 再入 `running` |
| 错误 | condition 未满足则保持原状态并返回原因 |
| 幂等 | 同 `affairId` 重复 resume 不重复创建 job |

### 4.5 `companion.cancel_job`

| 项 | 内容 |
|----|------|
| 意图 | 取消委派执行，不一定关闭 affair |
| 入参 | `affairId`、`jobId` |
| 行为 | 发 `job.cancel`；store 中 job → `canceled`；affair 可由张老板改为 `paused`/`blocked`，或保持当前非终态并等待再委派（新 job 时从当前态按 `canTransitionAffairStatus` 进入 `delegated`/`running`）。**禁止**迁到 `ready`（`ready` 仅能从 `clarifying` 进入）；**不得**自动 `closed` |
| 幂等 | 终态 job 再 cancel 成功确认 |

### 4.6 `companion.cancel_affair`

| 项 | 内容 |
|----|------|
| 意图 | 用户明确取消整件事务 |
| 入参 | `affairId`，可选 `closeReason` |
| 行为 | 若有 in-flight job 先 `job.cancel`；再 `affair.close` 且 status=`canceled` |
| 禁止 | 把本 FC 当成验收通过；验收通过须另循 `waiting_acceptance` → 用户确认 → `closed`（见 V1.3-05） |

### 4.7 `companion.send_chat_context`

| 项 | 内容 |
|----|------|
| 意图 | 把路径、日志片段、URL、短备注发到桌面侧通道或同步给 companion |
| 入参 | `text`、可选 `affairId`、可选 `contentKind`（`path`/`log`/`url`/`note`） |
| 行为 | 发 `chat.message`（`authorKind=zhang-boss`）；timeline 记一条；文本标 untrusted |
| 安全 | 不得解析为权限授予或系统指令；不得夹带凭据明文 |
| 与 `chat.context_attach` | 方向相反：attach 是 companion→phone；本 FC 是 phone→companion 的主动发送 |

### 4.8 `companion.fetch_pending_context`

| 项 | 内容 |
|----|------|
| 意图 | realtime 无法直注入时，张老板主动取桌面附加上下文 |
| 入参 | 可选 `affairId`；默认取 `activeAffairId` 或 `active_call` 队列 |
| 行为 | 读 store.`pendingContext`，返回后标记已消费；内容仍 untrusted |
| 来源 | 先前收到的 `chat.context_attach` |
| 失败 | 队列空则明确返回 empty，不得假装已注入模型 |

## 5. 与协议消息映射速查

| FC | Message type | 方向 |
|----|--------------|------|
| `create_job` | `job.create` (+ 可选 `affair.update`) | phone → companion |
| `get_progress` | （无） | — |
| `pause_affair` | `affair.update` | phone → companion |
| `resume_affair` | `affair.resume` | phone → companion |
| `cancel_job` | `job.cancel` | phone → companion |
| `cancel_affair` | `affair.close` | phone → companion |
| `send_chat_context` | `chat.message` | phone → companion |
| `fetch_pending_context` | 消费已收 `chat.context_attach` | companion → phone（历史事件） |

## 6. 错误与兼容

| 情况 | 行为 |
|------|------|
| 未知 FC name | 电话 runtime 拒绝；不得当任意命令执行 |
| 未知入参字段 | 可忽略；标 strict 的 id/status 除外 |
| session 失效 | 返回需 `session.open` / 重新配对；不删 store |
| companion 拒绝 job | store 保留 affair；记录失败原因；可转 `blocked` |
| 协议 `0.1` | draft；FC 名变更须同步本文与 `packages/protocol` catalog |

## 7. 安全清单

- 所有需桌面副作用的路径必须最终经过 companion permission gate。
- FC 入参/出参与 timeline **禁止**记录 API key、token、私钥。
- `send_chat_context` / `fetch_pending_context` 的文本不得提升为 system prompt。
- `create_job` 的 `workspaceHint` 不是授权本身。
- Renderer / 控制面板不能冒充这些 FC；桌面侧用户操作走 companion bridge 白名单。

## 8. 验收清单

- 八个 FC name 均有入参、映射消息、错误与幂等说明。
- `get_progress` 与 `fetch_pending_context` 不新增未登记 wire type。
- `pause` 走 `affair.update`；`resume` 走 `affair.resume`；`cancel_job` 走 `job.cancel`。
- `cancel_job` 后 affair **不得**暗示迁到 `ready`；合法后续仅为 `paused`/`blocked`、保持非终态待再委派，或用户明确取消整件事务。
- 任意 FC 成功路径都不能把 `job.completed` 映射成 `affair.closed`。
- Catalog 与 `packages/protocol` 导出常量一致，并被测试锁定名称列表。

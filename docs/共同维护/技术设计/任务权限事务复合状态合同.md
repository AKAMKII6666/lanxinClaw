# 任务/权限/事务复合状态合同

本合同约束 `affair / job / permission / UI action / 张老板话术` 五条状态链。任何跨链动作都必须携带证据，不允许只改其中一条链后让其它链自行猜测。

## 不变量

1. `job.completed` 只证明 worker 完成，不证明用户验收，也不得直接关闭 `affair`。
2. `affair.closed` / `affair.canceled` 是父终态。终态之后的 `job.accepted`、`job.progress`、`job.completed`、`job.failed`、`job.blocked` 不得复活或污染父事务。
3. `affair.cancel` 是复合动作：先持久化取消意图并失效权限，确认全部子 job 停止后提交父终态，再发送完整 `affair/jobs` 事实；不能以取消请求已接受替代停止证据。
4. `permission.allow_once` / `permission.allow_for_job` 是高风险动作。写 grant、调 delegator、调 OpenClaw 前必须重新验证：permission 仍 pending、job 仍 `needs_permission`、父 affair 仍可执行、job 是该 affair 的 current job。
5. `deny` / `require_more_context` 只对仍 pending 的 permission 生效。已经因父事务取消而 expired 的权限请求不得再广播 `job.failed`。
6. 非 current job 的迟到终态只能更新该 job 自身的历史事实，不得改写 `affair.status` 或 `currentJobId`。
7. UI action delivery 只证明用户意图已提交、排队或被拒绝，不证明业务状态已完成。
8. 张老板只能按工具回执和 `get_progress` 的当前证据回报。没有 create_job action receipt，不得声称任务已发；发现状态冲突时必须先说明冲突。

## 审查问题

| 问题 | 级别 | 必须修复动作 |
|------|------|--------------|
| 终态 affair 下的 job 事件能否把 UI 投影成 running/completed/blocked？ | P0 | 在 backend store 拒绝事件并记 audit/lastError；投影保持父终态 |
| 已取消 affair 的 pending permission 是否还能被 allow 并启动 OpenClaw？ | P0 | 在 bridge action policy 与 delegator 双层校验后拒绝，不写 grant、不调 adapter |
| `affair.cancel` 是否只写父状态而遗漏 current job 或 pending permission？ | P0 | 改为 job cancel/permission expire/affair close 的原子顺序；子动作失败则父状态不关闭 |
| 同一通电话内同一任务意图是否会产生多个有效 job？ | P1 | phone 侧生成 `taskIntentId` 并在发送前返回 duplicate |
| UI 是否会把一个重复任务的 completed 和另一个重复任务的 permission denied 混成同一详情？ | P1 | 列表显示处理中与最近终态；选中终态不自动跳转；详情绑定 affairId |
| 权限页“拒绝授权”和任务页“取消事务”是否表达成同一动作？ | P1 | 保持文案与动作分离；拒绝只失败 job，取消才关闭事务 |
| `requestAcceptance` 是否会在选中项丢失时回退到 `summaries[0]`？ | P1 | 必须绑定当前选中 affair；非 waiting_acceptance 明确 rejected |
| 历史镜像出现 `affair=canceled + job=completed` 是否被当成当前成功任务？ | P1 | 保持父终态与已完成子任务的历史事实；该组合本身合法，只有仍有非终态子 job 才提示冲突 |
| action delivery 文案是否被张老板说成业务完成？ | P2 | 工具提示与 action receipt 明确 delivery 只证明投递 |

## 兼容字段

`JobPayload.taskIntentId` 是可选字段，由 phone 侧在 `companion.create_job` 生成。新端用它识别同一通电话内的重复任务意图；旧端没有该字段时仍按 `messageId/jobId` 幂等。

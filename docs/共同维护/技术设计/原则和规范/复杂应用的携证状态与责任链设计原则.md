# 复杂应用的携证状态与责任链设计原则

## 0. 目标

本原则用于多主体、异步、跨系统、长事务应用。

它不是通用“最佳实践”清单，而是一套审查法则：帮助实施者判断什么时候必须启用复杂系统约束，什么情况算问题，问题有多严重，以及最低修复必须做到哪里。

一句话目标：

> 在多主体、异步、跨边界、长事务系统里，让状态可信、责任不断、失败可见、恢复可控。

## 1. 典型适用场景

出现下列任一情形时，应主动使用本文：

- 一个业务动作跨越两个以上系统、进程、服务、设备或人机角色。
- 状态由外部服务、AI Agent、硬件设备、队列、回调、用户确认或后台任务共同影响。
- 存在权限、资金、文件、命令、网络、账号、隐私、长期任务等高风险副作用。
- “成功、失败、阻塞、等待”会影响用户决策或后续自动动作。
- 系统需要重试、恢复、监督、回报、补偿或审计。

默认不适用：

- 单进程内的纯 UI 展示状态。
- 无副作用、可重复、失败成本很低的小函数。
- 临时脚本或一次性数据清洗，且结果不会驱动后续自动动作。
- 已被上游强契约完整托管的简单 CRUD。

## 2. 严重级别

P0：可能造成误执行、越权、数据破坏、资金损失、隐私泄露、不可逆错误，或把未完成任务宣布为完成。必须立即修。

P1：状态不可信、失败被吞、恢复不可解释、跨层契约不一致、异步消息可能串线或覆盖正确状态。必须在本轮修完。

P2：可观测性不足、错误分类不细、文案不清、测试覆盖薄弱、结构可维护性下降。应排期修，但不一定阻塞本轮。

## 3. 原则一：状态是主张，主张必须携证

任何系统状态都不是单纯字段值，而是一个 claim。系统说“完成、失败、阻塞、等待授权”，必须能说明它基于什么观测、谁观测、什么时候观测、为什么足够。

触发条件：

- 状态会影响下一步自动动作。
- 状态会展示给用户、运营、责任人或外部系统。
- 状态来自外部系统、AI 回复、异步事件、日志、队列或探针。

核心禁令：

- 禁止用弱文本直接证明成功。
- 禁止把“调用返回 ok”直接等同于“业务完成”。
- 禁止没有 observedAt、source、correlation 的状态进入核心状态机。
- 禁止多个证据冲突时默认采纳乐观结果。

问题判定：

- P0：任务实际未完成，但系统进入 completed、closed、settled、published 等成功终态。
- P1：状态迁移没有证据来源或无法回放原因。
- P1：弱证据证明成功，强证据显示失败却被忽略。
- P2：状态有证据，但 reasonCode、摘要或时间缺失。

最低修复：

- 引入 evidence/decision 层。
- 每次状态迁移记录 source、observedAt、reasonCode、correlationId。
- 成功必须由结构化或中强证据证明；弱文本只能辅助解释或识别异常。

测试要求：

- 正例：强证据完成才进入 completed。
- 反例：最终文本说完成但工具失败，不得 completed。
- 反例：证据不足时只能 running、unknown、blocked 或等待人工确认，不能成功。

## 4. 原则二：跨边界必须防腐

外部系统的状态、异常、字段、枚举、权限，不得直接进入内部核心模型。

触发条件：

- 接入第三方 API、执行引擎、AI Agent、硬件设备、支付、浏览器、文件系统、命令执行。
- 外部系统有自己的状态机、权限模型或错误码。
- 内部业务需要长期维护自己的语义。

核心禁令：

- 禁止外部枚举直接污染内部领域状态。
- 禁止第三方异常原样展示给用户。
- 禁止外部权限名直接等同内部授权。
- 禁止业务层和 UI 层到处识别第三方字段名。

问题判定：

- P1：外部 `completed` 直接写内部 `completed`，没有内部裁决。
- P1：外部错误原样穿透，未分类、未脱敏、未标 retryable。
- P1：第三方权限被当成本系统授权事实。
- P2：UI 或业务层大量依赖第三方字段名。

最低修复：

- 建立 adapter 或 anti-corruption layer。
- 外部响应先归一为 internal claim + evidence + reasonCode。
- 错误进入内部前必须分类、脱敏、标记可重试性。
- 外部字段只在 adapter 边界内扩散。

测试要求：

- 第三方未知状态不得进入核心状态机。
- 第三方错误不得泄露 token、secret、路径或敏感载荷。
- 外部 completed 与内部 completed 之间必须经过 decision 层。

## 5. 原则三：长事务必须有责任人和过程管理器

跨系统任务不是一次函数调用，而是长事务。它需要明确的 Process Manager 或 Saga 管理推进、暂停、恢复、补偿和回报。

触发条件：

- 任务包含用户确认、权限授权、异步执行、后台监督、失败恢复。
- 任务可能跨重启、断线、回调或多轮对话。
- 一个动作完成后还有验收、通知、补偿或后续步骤。

核心禁令：

- 禁止把长事务藏在一次函数调用里。
- 禁止只依赖内存状态推进关键业务。
- 禁止失败只写日志，不进入业务状态。
- 禁止没有责任 owner 的后台任务长期运行。

问题判定：

- P0：重试导致不可逆副作用重复执行。
- P1：进程重启后不知道任务处于哪一步。
- P1：用户授权后任务丢失，系统无法解释。
- P1：任务失败没有人或模块负责回报和恢复。
- P2：有过程状态，但缺少恢复扫描或超时策略。

最低修复：

- 引入 affair、job、processId、operationId 或等价长事务标识。
- 每步有 step state、idempotency key、correlationId。
- 启动时能恢复 in-flight 流程。
- 失败进入明确业务状态，并能通知责任人或用户。

测试要求：

- 重启恢复不重复创建副作用。
- 授权后执行失败进入可见失败状态。
- 超时、取消、恢复都有明确状态边。

## 6. 原则四：终态必须单调，迟到消息不得复活

completed、failed、canceled、closed、revoked、settled 等终态必须受门闩保护。异步系统默认会有迟到、重复、乱序消息。

触发条件：

- 使用 WebSocket、队列、轮询、回调、后台任务、远程执行。
- 存在 cancel、timeout、retry、reconnect。
- 同一个对象可能被多个来源更新。

核心禁令：

- 禁止终态被 running、progress、pending 覆盖。
- 禁止 cancel 后被迟到 completed 复活。
- 禁止无版本、无时间、无 correlation 的异步更新改核心状态。
- 禁止已撤销身份、已关闭事务或已结算账务被普通事件恢复。

问题判定：

- P0：取消或撤销后仍继续执行高风险副作用。
- P1：终态被迟到消息覆盖。
- P1：不同 job、run、session、tenant 的消息串线。
- P2：重复消息能产生重复通知或重复 UI 闪动。

最低修复：

- 终态门闩。
- messageId 幂等。
- runId、jobId、sessionKey、tenantId、generationId 等归属校验。
- 状态迁移必须经过 canTransition 或等价守卫。

测试要求：

- canceled 后收到 completed，不得复活。
- completed 后收到 running，不得降级。
- 不同任务的 run snapshot 不得更新当前任务。

## 7. 原则五：权限和副作用必须 fail-closed

只要系统能读写文件、执行命令、控制设备、访问网络、读取凭据、改变账号状态、发布内容或触发账务，就必须默认拒绝。

触发条件：

- 能控制外部资源或真实环境。
- 用户授权、设备配对、任务委派、工具调用。
- 权限来自自然语言、模型推断、配置、缓存或外部系统。

核心禁令：

- 禁止未知权限默认通过。
- 禁止空权限列表委派执行。
- 禁止 mock、fallback、降级路径绕过权限。
- 禁止把 scope hint、workspace hint、display name、UI 状态当授权。

问题判定：

- P0：未授权执行写入、命令、桌面控制、凭据读取、发布、扣费。
- P1：未知权限或空权限被传到执行层。
- P1：权限校验只在 UI，不在服务端或可信边界。
- P1：真实服务故障后降级到更宽松模式继续执行。
- P2：拒绝原因不清，用户不知道如何恢复。

最低修复：

- 明确权限枚举和权限 owner。
- 所有执行入口统一过权限门。
- 权限失败投影为业务状态。
- 用户可见原因脱敏、稳定、可回报。

测试要求：

- 未知权限 fail-closed。
- 空权限 fail-closed。
- UI 绕过请求仍被服务端拒绝。
- Mock 或本地 fallback 不能扩大权限。

## 8. 原则六：失败必须产品化

失败不是异常，不是日志，不是“稍后再说”。失败是系统状态的一部分，必须能被用户、责任人和开发者同时理解。

触发条件：

- 失败影响任务完成、用户等待、后续自动动作。
- 失败来自外部服务、工具、网络、权限、策略、超时。
- 失败可能需要用户介入。

核心禁令：

- 禁止 catch 后静默继续。
- 禁止无限轮询但不改变用户可见状态。
- 禁止只记录日志，不广播状态。
- 禁止把所有失败都叫 unknown error。
- 禁止错误文本泄露凭据或敏感数据。

问题判定：

- P1：执行失败没有进入 failed、blocked、needs_permission 等业务状态。
- P1：非可重试失败仍持续轮询。
- P1：错误含凭据或敏感路径直接外显。
- P2：失败没有 reasonCode、retryable、resumeCondition。

最低修复：

- 建立失败分类：retryable、non-retryable、blocked、needs_permission、timeout、insufficient_evidence。
- 失败进入业务状态并触发监督或通知。
- 错误文本统一脱敏。
- 用户能知道“现在卡在哪里，下一步要谁做什么”。

测试要求：

- 非可重试失败停止普通轮询并进入失败状态。
- 权限阻塞与系统失败分开投影。
- 用户可见错误不含 token、secret、api key。

## 9. 原则七：Mock 不得掩盖真实失败

Mock 是契约工具，不是乐观演示。它必须暴露真实系统可能失败的路径。

触发条件：

- mock companion、fake transport、local runtime、测试替身。
- 真实系统有权限、网络、超时、协议错误、状态乱序。
- mock 被用于联调前验收。

核心禁令：

- 禁止真实 runtime 不可用时自动 fallback 到 mock 并报告成功。
- 禁止 mock 只覆盖 happy path。
- 禁止 mock 的状态比真实协议更宽松。
- 禁止 mock 验收替代真实链路验收。

问题判定：

- P1：真实连接失败但系统切 mock 后显示成功。
- P1：mock 接受真实 schema 会拒绝的消息。
- P2：mock 没有 blocked、failed、timeout、canceled、stale 场景。

最低修复：

- mock 与 schema、validator 共享契约。
- fake transport 必须能模拟失败、乱序、迟到、超时。
- runtime 缺配置必须 fail-closed。

测试要求：

- 缺真实配置时必须失败，不能回退成功。
- mock 正反例与真实协议一致。
- fake transport 能模拟关键坏路径。

## 10. 原则八：契约必须同步变更

协议、类型、schema、mock、真实实现、UI、测试是同一个契约的不同投影，不能只改一处。

触发条件：

- 新增字段、新增状态、新增 message type、新增权限、新增错误码。
- 改变状态语义、方向、认证要求、兼容策略。
- 多层系统都依赖该字段或状态。

核心禁令：

- 禁止只改 TypeScript type，不改 JSON Schema。
- 禁止只改实现，不改协议文档和例子。
- 禁止 UI 展示依赖未进协议的临时字段。
- 禁止消息方向、owner、认证要求不明。

问题判定：

- P1：某层能发出另一层无法校验的消息。
- P1：新增状态没有状态机合法边。
- P1：安全字段没有 owner、方向、认证要求。
- P2：文档、example、mock 滞后。

最低修复：

- 同步 type、schema、validator、example、mock、tests、docs。
- 每个字段声明 owner、方向、认证、兼容策略。
- 正反例测试覆盖跨层消费。

测试要求：

- 新消息 example 必须通过 validator。
- 非法状态组合必须被拒绝。
- Mock 与真实实现消费同一契约。

## 11. 原则九：观测和审计必须能还原因果

复杂系统不能只看当前状态，必须能回答“为什么变成这样”。

触发条件：

- 状态由多个异步来源产生。
- 用户可能质疑任务结果。
- 开发者需要真机联调。
- 系统包含自动执行、权限边界或长期任务。

核心禁令：

- 禁止没有 correlationId 的关键事件。
- 禁止日志里缺少核心业务 id。
- 禁止审计记录包含凭据。
- 禁止只记录结果，不记录被拒绝的证据或迁移。

问题判定：

- P1：误判状态后无法追溯采纳了哪条证据。
- P1：跨系统任务无法按同一 id 串起来。
- P1：日志或审计泄露 API key、token、secret、私钥。
- P2：日志有信息，但用户可见状态无法解释。

最低修复：

- 关键路径统一携带业务 id、操作 id、会话 id、外部执行 id。
- 状态裁决记录 reasonCode、observedAt、evidenceKind。
- 日志和用户摘要都脱敏。
- 被拒绝的迟到消息、非法迁移也要能诊断。

测试要求：

- 失败状态能追到原因码。
- 脱敏测试覆盖日志、审计和用户摘要。
- 异步链路具备端到端关联 id。

## 12. 原则十：责任链必须完整闭环

复杂系统里的“责任人”不一定是人，也可以是模块、服务、后台监督器或 AI 角色。关键是每个阶段都要知道谁负责下一步。

触发条件：

- 一个任务需要跨用户、模型、服务、执行器、后台监督或人工验收。
- 执行结果需要回报、确认、继续、取消或补救。
- 系统允许用户暂时离开，后台继续推进。

核心禁令：

- 禁止任务交给下游后无人监督。
- 禁止失败后不知道由谁回报。
- 禁止完成后没有验收或关闭策略。
- 禁止“等待用户”没有恢复入口或恢复条件。

问题判定：

- P1：任务已经执行，但无人负责监督结果。
- P1：任务阻塞后用户不可见，责任人不可见。
- P1：完成态直接关闭，跳过必要验收。
- P2：回报文案不清，不能指导下一步。

最低修复：

- 为每个长事务声明 owner。
- 建立监督 loop 或状态探针。
- blocked、failed、completed、needs_permission 都有回报策略。
- 完成后进入验收或明确关闭策略。

测试要求：

- 执行失败会触发回报动作或可观察状态。
- completed 不自动越过验收边界。
- blocked 有 resumeCondition 或等价恢复说明。

## 13. 设计前检查表

设计或改造复杂功能前，先回答：

- 内部领域状态机是什么？
- 外部系统有哪些状态、事件和证据来源？
- 哪些状态是成功、失败、阻塞、等待、终态？
- 哪些状态会驱动真实副作用？
- 谁是每个业务事实的 owner？
- 哪些边界需要 adapter 或防腐层？
- 哪些步骤需要 idempotency key？
- 哪些消息可能迟到、重复、乱序或串线？
- 失败如何分类、投影、通知和恢复？
- 完成后是否需要验收？
- Mock、schema、类型、实现、UI、测试是否同步？
- 用户和开发者如何追溯“为什么变成这个状态”？

当发现问题时，避免只说“这里要注意状态一致性”。应写成可执行的判定：

```markdown
### 不需要做
- 不需要引入的过度机制：

```

## 15. 最终验收标准

复杂状态适配系统的验收标准不是“能跑通一次”，而是：

> 系统在成功、失败、阻塞、取消、超时、重启、乱序、重复、权限不足时，都不会说谎，并且能告诉责任人下一步该做什么。

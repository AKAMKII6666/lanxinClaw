# 高风险边界与携证状态转移原则

## 0. 文档定位

本文用于指导高风险应用的需求分析、方案设计、执行计划、协议对齐和代码审查。

本文是软监督原则，不替代具体项目已经固化的产品需求、协议、schema、状态机、安全模型或代码规范：

- 具体字段、枚举、错误码、接口行为、计费时点和权限口径，以当前项目真源为准。
- 不因形式上没有完全采用本文而自动阻断开发。
- 若分析确认触及权限绕过、错误扣费、错误发布、数据破坏、隐私泄露、不可逆状态破坏等硬风险，阻断原因来自这些真实风险及项目硬规则，而不是来自本文的形式要求。
- 采用额外字段、代际、围栏、日志或审计前，必须说明它关闭的具体失败路径；不得为了“看起来更安全”增加无人校验、无人消费、无人审计的字段。

本文只固化抽象原则。针对具体业务、前端、后端、Mock、Webhook、执行引擎、硬件设备或展示链路的细则，应在具体项目中另行制定。

## 1. 核心抽象：携证状态转移

**携证状态转移** 指：

> 每一次跨边界或高风险状态推进，都必须携带足以判断“身份正确、对象正确、归属正确、上下文仍有效、前置条件已满足、操作仍允许”的证据；接收方必须验证这些条件后，才能提交状态变化。

这里的“证”不等同于密码学证明。它可以是：

- 可信会话提供的用户、组织、租户或设备身份；
- 可关联的资源、任务、意图、请求、会话或代际标识；
- 上游可信服务作出的状态断言；
- 接收方能够独立复验的外部事实；
- 数据库中可原子检查的当前状态；
- 能够证明请求未过期、未取消、未被替代的围栏条件；
- 脱敏的审计、时间线、决策记录或错误码。

携证状态转移主要防止：

- 中间步骤被误判为业务完成；
- 迟到、重复或重放消息推进旧状态；
- 错误用户、错误租户、错误设备或错误资源被修改；
- 部分成功被展示为完整成功；
- 同一业务意图被重复执行、重复扣费或重复发布；
- 配置错误、Mock 或默认值制造“假成功”；
- 事故发生后无法还原当时为何允许该状态转移。

## 2. 基本判断

对任何高风险状态转移，至少回答：

1. 谁在操作：可信身份和归属从哪里来？
2. 操作什么：业务资源、任务、意图和请求如何关联？
3. 针对哪一代：如何判断结果仍属于当前有效上下文？
4. 凭什么推进：哪些前置事实已经确认？
5. 现在还能否执行：是否已取消、超时、完成、撤销或被替代？
6. 重复执行会怎样：是否幂等，是否可能产生重复副作用？
7. 失败一半会怎样：是否留下假成功、半完成或无法恢复的状态？
8. 之后如何解释：是否能追踪当时的判断依据和状态变化？

无法回答的问题，不应被一句“后面再看”“一般没事”带过。应明确记录风险、补偿控制和裁决。

## 3. 适用范围

出现下列任一情形时，应主动应用本文：

- 跨服务请求、Webhook、回调、轮询结果、队列消息、WebSocket 消息或异步事件；
- 身份、权限、租户归属、设备归属或资源归属判断；
- 支付、扣费、占用、结算、退款或其他账务动作；
- 发布、激活、恢复、取消、删除、关闭或不可逆终态；
- 多候选、多版本、多代际、共享资源或竞争更新；
- Retry、幂等、重复提交、并发竞争或迟到结果；
- Mock、Fake、Stub、开发模式与真实后端切换；
- development、staging、production 等环境与高风险配置；
- 会直接影响终端用户体验、外部系统状态或真实资源的链路；
- 协议正文、类型、Mock、示例、mapper、测试和实现之间的同步。

纯文案、样式、无状态展示、低风险局部纯函数和不跨越上述边界的一次性脚本，默认不需要扩大应用本文。

## 4. 十二条原则

### 原则 1：成功态必须有完整门闩

任何用户可见或不可逆成功态，只能在全部必要前置条件确认后写入。

核心禁令：

- 中间信号不能单独证明业务完成。
- 非空标识、URL、单个回调、日志片段或默认值不能自动证明资源可用。
- 部分步骤成功时不得提前展示完整成功。
- 成功门闩必须对应成功态的真实业务含义。

问题判定：

- P0：任务、发布、扣费或关闭实际未完成，但系统进入成功或终态。
- P1：成功态依赖单一弱信号，缺少完整前置事实。
- P2：成功态可用，但缺少可解释摘要、理由码或观测时间。

最低修复：

- 列出成功态所需前置条件。
- 把前置条件放入同一受控事务、状态机守卫或可验证的决策层。
- 增加反例测试，证明部分成功不能进入完整成功。

### 原则 2：跨边界消息必须可关联、可判旧

所有可能延迟、重试或重放的消息，必须能够关联到可信身份、业务资源、业务意图、任务和有效代际。

核心禁令：

- 不得仅凭“它是在上一调用之后到达的”推断消息仍然有效。
- 已取消、已恢复、已换源、已超时或已被替代的旧消息不得推进当前状态。
- 不同用户、租户、设备、资源、任务或会话的消息不得串线。

问题判定：

- P0：旧消息或串线消息触发真实副作用。
- P1：消息缺少 correlation id、resource id、generation id 或等价关联证据。
- P2：消息能去重但缺少足够审计上下文。

最低修复：

- 引入 messageId、correlationId、resourceId、taskId、sessionId、generationId 或等价标识。
- 接收方基于当前真源验证消息是否仍有效。
- 重复消息必须幂等，迟到消息必须被拒绝或只作审计。

### 原则 3：不可逆副作用必须先验证后提交

扣费、发布、激活、恢复、取消、删除、写入、命令执行、外部账号变更等动作，必须先完成必要校验，再提交状态变化。

核心禁令：

- 不得先写成功态，再补校验。
- 不得让 UI、客户端缓存或弱上下文替代服务端校验。
- 任一步失败时，不得留下对外可见的半完成成功态。

问题判定：

- P0：未校验身份、权限或归属即执行不可逆副作用。
- P1：校验和提交不是同一受控流程，存在竞争窗口。
- P2：有校验但失败恢复和审计不足。

最低修复：

- 将校验与提交放入事务、条件更新、受控状态迁移或统一命令处理器。
- 为副作用建立幂等键和补偿策略。
- 测试并发、重复提交和中途失败。

### 原则 4：终态和账务状态必须单调

不可逆终态不得复活；账务历史不得通过覆盖或删除改写。

核心禁令：

- 已完成、已失败、已取消、已关闭、已结算的状态不得被普通进度覆盖。
- 重复请求、重复回调和 Retry 不得重复产生同一副作用。
- Cancel、超时、撤销等不可逆终态不得被 worker、补偿或迟到消息覆盖。

问题判定：

- P0：取消后仍继续执行高风险副作用，或同一意图重复扣费。
- P1：终态被迟到消息覆盖。
- P1：账务历史可被覆盖式更新改写。
- P2：重复事件导致重复通知或 UI 闪烁。

最低修复：

- 建立终态门闩和合法状态边。
- 每个不可逆副作用有幂等键。
- 迟到事件只能被拒绝、审计或投影为无副作用信息。

### 原则 5：业务事实必须有唯一真源

技术处理状态、候选结果、预览内容、当前生效内容、资源可交付性、账务状态和操作能力是不同业务事实，应明确区分。

核心禁令：

- 禁止从一个宽泛状态推断多个独立事实。
- 禁止多个服务各自猜测同一事实。
- 禁止由展示层反向决定权限、账务、执行或关闭事实。

问题判定：

- P1：同一业务事实存在多个可写真源。
- P1：调用方从外部系统宽泛状态直接推导内部业务事实。
- P2：派生状态没有写明输入真源和映射规则。

最低修复：

- 标出每个业务事实的 owner。
- 派生状态必须经过 mapper 或 decision 层。
- 多个真源冲突时必须先裁决，不得由调用方自行猜测。

### 原则 6：配置与安全边界 fail-closed

环境、后端模式、身份、权限、凭据和高风险配置缺失、非法或无法判断时，必须拒绝启动或拒绝操作。

核心禁令：

- 禁止静默回落到 development、Mock 或更宽松权限。
- 禁止用“不等于 production”代表 development。
- 禁止客户端隐藏、按钮不可见和默认值代替服务端门禁。
- 构建、启动脚本和运行时代码对环境的理解必须一致。

问题判定：

- P0：配置缺失导致越权、数据破坏、错误账务或隐私泄露。
- P1：真实服务故障时自动切到 Mock 并报告成功。
- P1：权限缺失时仍进入执行层。
- P2：配置失败可见性不足。

最低修复：

- 关键配置缺失时显式失败。
- Mock、开发模式、真实模式必须有清晰开关和可观测状态。
- 服务端或可信执行边界重新校验权限和能力。

### 原则 7：展示增强链路可以 fail-open，但不得伪装控制面

直接影响用户浏览、播放、预览或读取体验的非关键增强链路，在优化资源不可用、预检失败、网络超时或映射缺失时，可以保留原内容并安全退出。

核心禁令：

- fail-open 不得绕过身份、账务、权限、写入、发布或执行门禁。
- 增强失败不得损害原有能力。
- 不确定是否可安全替换时，应保持原内容。

问题判定：

- P1：展示增强失败破坏原有体验。
- P1：借 fail-open 绕过控制面校验。
- P2：降级文案或诊断不足。

最低修复：

- 明确控制面和展示面的边界。
- 展示增强失败只恢复原内容，不写业务成功态。
- 记录脱敏诊断，便于排障。

### 原则 8：Mock 不得作为运行时降级

Mock 只能在明确允许的开发、测试或演示配置中启用，不能用于掩盖真实服务故障。

核心禁令：

- 真实服务超时、错误或解析失败必须暴露。
- 禁止运行时静默切换到 Mock 并继续报告成功。
- Mock 验收不能替代真实链路验收。

问题判定：

- P1：真实连接失败但系统切 Mock 后显示成功。
- P1：Mock 接受真实 schema 会拒绝的消息。
- P2：Mock 没有覆盖失败、阻塞、取消、超时、乱序场景。

最低修复：

- Mock 与真实接口保持外部合同同构。
- Fake transport 必须能模拟失败、乱序、迟到、超时。
- 真实 runtime 缺配置必须 fail-closed。

### 原则 9：操作能力由可信 owner 显式决定

Retry、Cancel、Restore、Apply、Close、Approve 等能力，应由可信 owner 的当前状态决定，并在动作执行时重新校验。

核心禁令：

- 前端不得仅靠按钮可见性、本地缓存或宽泛状态推断权限。
- 外部调用方不得推断“模型同意”就代表系统已授权。
- 能力展示与执行校验不得分离成两套规则。

问题判定：

- P0：未授权能力被执行。
- P1：展示可操作但服务端实际规则不同，导致误导或绕过。
- P2：拒绝原因不清，用户不知道如何恢复。

最低修复：

- 建立能力查询或能力投影。
- 动作执行时重新读取可信状态并校验。
- 拒绝要有稳定错误码和用户可理解原因。

### 原则 10：高风险链路必须包含反例测试

测试不仅要证明正常路径能够完成，还要证明错误输入和异常时序不能推进错误状态。

至少按风险覆盖：

- 重复提交与重复回调；
- 并发竞争；
- 迟到结果与旧代际；
- 超时与部分成功；
- 非法或缺失配置；
- 未知协议状态；
- 跨租户、跨设备或跨资源访问；
- 下游不可用；
- 事务中途失败。

问题判定：

- P1：高风险迁移只有 happy path 测试。
- P1：已知危险反例没有测试。
- P2：测试覆盖了错误路径，但断言不够精确。

最低修复：

- 每个高风险状态迁移至少有一个正例和一个反例。
- 反例测试要断言“不推进状态”和“不产生副作用”。
- 对异步链路增加重复、迟到、取消、超时测试。

### 原则 11：协议载体必须一致

协议正文、字段表、错误码、HTTP 状态码、JSON 示例、时序图、Mock fixture、Wire DTO、mapper 和测试必须表达同一合同。

核心禁令：

- 示例不能成为第二套协议。
- 不得只修改正文而遗漏类型、Mock 或映射。
- 不得用本地实现反向覆盖已明确的协议语义。
- 新字段不得缺少 owner、方向、认证要求和兼容策略。

问题判定：

- P1：某层能发出另一层无法校验的消息。
- P1：新增状态没有合法状态边。
- P1：安全字段没有 owner、方向或认证要求。
- P2：文档、example、mock、测试滞后。

最低修复：

- 同步 type、schema、validator、example、mock、tests、docs。
- 每个新增字段说明 owner、方向、认证、兼容策略。
- 正反例测试覆盖跨层消费。

### 原则 12：关键动作必须可追踪

异步和高风险链路应保留足够且脱敏的关联上下文，以便还原“为何允许或拒绝这次操作”。

可追踪信息应按实际需要选择：

- 可信身份、用户、租户、设备或会话；
- 业务资源、任务、意图和有效代际；
- 状态迁移前后值；
- 机器可读错误码；
- 请求关联标识；
- 关键前置检查结果；
- 采纳或拒绝的证据摘要。

问题判定：

- P1：误判状态后无法追溯采纳了哪条证据。
- P1：跨系统任务无法按同一 id 串起来。
- P1：日志或审计泄露密钥、令牌、私钥或敏感数据。
- P2：日志有信息，但用户可见状态无法解释。

最低修复：

- 关键路径统一携带必要关联 id。
- 状态裁决记录 reasonCode、observedAt、evidenceKind。
- 日志、审计和用户摘要都必须脱敏。
- 被拒绝的迟到消息、非法迁移也要能诊断。

## 5. 证据、断言与独立验证

为避免“增加字段就是增加安全性”的机械做法，必须区分三种信息：

| 类型 | 含义 | 接收方应如何处理 |
|------|------|------------------|
| 业务事实 | 系统当前权威状态 | 从唯一真源读取或在事务内确认 |
| 受信断言 | 经认证的上游服务声明某事实成立 | 校验发送方身份、对象关联和时效后使用 |
| 独立验证 | 接收方使用自身权限重新核实外部事实 | 适用于接收方具备验证能力且风险值得承担成本的场景 |

一个布尔值、状态值或时间字段通常只是受信断言或审计上下文，不会因为被写入请求就自动成为独立证明。

是否需要新增证据字段，应回答：

1. 字段由谁生产？
2. 谁消费、校验、存储或审计？
3. 它关闭了哪一种真实歧义或风险？
4. 缺少它时，能否由已有真源安全判断？
5. 它如何与资源、任务、意图和代际关联？
6. 伪造、缺失、过期或冲突时如何处理？

若没有组件读取、校验、存储或审计某字段，也无法说明它关闭的风险，则不得仅以“更完整”为由将其设为高风险必填项。

## 6. 控制面与展示面的失败策略

### 6.1 控制面：默认 fail-closed

以下场景无法确认时，默认拒绝：

- 身份和归属；
- 权限和操作能力；
- 账务前置条件；
- 当前代际；
- 不可逆状态迁移；
- 运行环境和后端模式；
- 发布、激活、写入或执行所需的可交付条件。

### 6.2 展示面：可安全 fail-open

以下增强能力失败时，可以保留原始体验：

- 非关键资源加载；
- 非关键展示增强；
- 预览、预检、播放探测或只读辅助展示；
- 不驱动业务状态的本地投影。

### 6.3 边界

fail-open 只表示“保留原内容或原能力”，不表示：

- 绕过身份校验；
- 绕过账务门闩；
- 使用未经确认的优化资源；
- 在失败时静默写入业务成功态。

## 7. 方案和计划制定时的应用方式

涉及本文适用范围的方案，应增加一个简短的“高风险边界检查”，至少说明：

1. 本次涉及哪些跨边界或不可逆状态转移；
2. 每个状态转移的可信身份和资源归属来源；
3. 成功态门闩及其证据来源；
4. 幂等键、意图、任务和代际如何关联；
5. 重复、迟到、取消、超时和部分成功如何处理；
6. 控制面与展示面分别采用何种失败策略；
7. Mock、真实后端、协议和前端是否保持同一外部合同；
8. 哪些反例测试证明错误状态无法被推进；
9. 哪些信息用于联调和事后追踪。

若某项不适用，应说明“不适用”的原因，无需为了形式补造机制。

## 8. 冲突分析与裁决

当方案、协议、现有实现或开发成本与本文发生张力时，不得默默选择一方。应按以下格式呈现：

```markdown
### 冲突
- 当前方案：
- 触发原则：
- 可能风险：
- 现有补偿控制：

### 选项
1. 方案 A：影响范围、收益、成本和残余风险
2. 方案 B：影响范围、收益、成本和残余风险

### 建议
- 推荐：
- 理由：
- 是否触及现有硬规则或协议：
- 若暂缓，如何登记和验证：
```

裁决优先级：

1. 安全、身份、权限、租户隔离和数据正确性；
2. 账务正确性与不可逆状态安全；
3. 已封版协议和明确业务真源；
4. 可恢复性、可测试性和可观测性；
5. 实现复杂度与交付效率；
6. 局部代码风格。

## 9. 软监督与阻断边界

### 9.1 本文不会单独阻断的情况

- 字段命名、代码形式或实现方式不同，但满足同一不变量；
- 已有机制能够提供等价的身份、关联、围栏或幂等保证；
- 低风险局部功能没有跨边界或不可逆状态；
- 仅为未来扩展、审计便利或信息更完整的建议；
- 无法证明会造成错误状态推进的防御性增强。

### 9.2 需要升级处理的情况

若分析确认存在以下风险，应按现有安全、协议或质量规则处理，而不能以“本文是软监督”为由忽略：

- 跨租户、跨设备或跨资源访问；
- 鉴权或权限绕过；
- 重复扣费、错误扣费或账务历史被改写；
- 旧代际、已取消或已超时结果重新生效；
- 未满足完整门闩即发布、激活或展示业务成功；
- production 静默进入 development、Mock 或宽松模式；
- 用户原有能力被增强脚本破坏；
- 不可逆终态可以被复活。

## 10. 禁止机械套用

本文不是“字段越多越安全”“事务越大越安全”或“所有状态都要永久保存”的依据。

禁止：

- 为了看起来符合原则而新增无人消费的字段；
- 把受信断言描述成接收方已经独立验证；
- 在不存在并发、迟到或多候选问题时强行引入复杂代际模型；
- 用本原则覆盖当前协议中的明确业务合同；
- 把未来增强包装成当前 P0/P1；
- 为低风险 UI 或局部逻辑引入不成比例的分布式基础设施；
- 只增加日志而不建立实际校验；
- 只隐藏前端入口而不保护服务端高风险动作。

采用额外机制前，应说明它关闭的具体失败路径及现有机制为何不足。

## 11. 方案速查清单

- [ ] 成功态是否由完整门闩决定？
- [ ] 消息是否能够关联正确身份、资源、任务、意图和代际？
- [ ] 接收方是否会验证，而不只是接收这些字段？
- [ ] 重复、迟到和并发情况下是否仍安全？
- [ ] 不可逆副作用是否先验证后提交？
- [ ] 终态和账务历史是否保持单调？
- [ ] active、preview、candidate、ready、billed 等独立事实是否有唯一真源？
- [ ] 配置错误是否显式失败？
- [ ] Mock 是否可能掩盖真实服务故障？
- [ ] 服务端或可信边界是否重新校验操作能力？
- [ ] 展示增强失败是否保留原体验？
- [ ] 是否有反例测试证明错误状态不能被推进？
- [ ] 协议、类型、Mock、mapper、示例和测试是否一致？
- [ ] 关键决策是否可追踪且已脱敏？
